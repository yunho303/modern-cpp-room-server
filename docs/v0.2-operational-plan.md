## 4주차 코드 질문과 답

### 1. span은 소유권이 없는데 co_await 동안 왜 안전한가?

[Session writer](../src/network/session.cpp)의 `packet_batch`와 `write_buffers`는 coroutine의 지역 상태입니다.
`packet_batch`의 SharedPacket이 실제 immutable payload를 소유하고, write가 완료된 뒤에만 reset합니다.
writer 완료 handler가 Session의 shared_ptr도 보유합니다. span이나 const_buffer가 수명을 보장하는 것이 아니라,
이를 뒷받침하는 소유 객체가 작업 완료까지 살아 있어 안전합니다.

### 2. 여러 buffer의 패킷 순서는 왜 유지되는가?

OutboundQueue에서 FIFO로 꺼낸 순서대로 buffer sequence를 구성합니다. 한 Session에서는 writer가 하나이고,
이전 async_write의 완료를 기다린 다음 batch를 시작합니다. TCP는 이 바이트 스트림의 순서를 유지합니다.
수신 측에서 read 한 번이 패킷 하나라는 보장은 없으므로 기존 length framing은 계속 필요합니다.
이는 현재 Session 안의 순서에 대한 설명이며, 미래의 여러 생산자 사이에 전역 이벤트 순서가 자동으로 생긴다는
의미는 아닙니다.

### 3. async_write 한 번은 OS 송신 함수 한 번인가?

아닙니다. 여러 async_write_some으로 구성될 수 있는 composed operation입니다. 따라서 batch 시작 횟수,
하위 write 호출 횟수, OS 송신 호출 횟수, TCP segment 수는 구분해야 합니다. 완료 바이트 역시 상대 application이
해당 데이터를 처리했다는 ACK가 아닙니다.
[Asio async_write 계약](https://think-async.com/Asio/asio-1.36.0/doc/asio/reference/async_write/overload1.html)

### 4. 64개와 64KiB 두 제한이 필요한 이유는?

개수 제한은 buffer descriptor 수와 batch 구성 작업을, byte 제한은 한 batch가 붙잡는 payload 양을 제한합니다.
현재 pop_batch는 첫 패킷이 byte 제한보다 큰 경우 그 한 개를 허용해 진행 불능을 피합니다.
현재 protocol은 payload 64KiB에 header 6바이트가 추가되므로, 정확한 최대 packet은 65,542바이트입니다.
batch 상한을 항상 정확히 64KiB라고 설명하면 이 예외가 빠집니다.

### 5. pending_bytes가 송신 중 batch를 제외해도 괜찮은가?

이 값을 **Queue 안에서 기다리는 바이트**로 정의하는 것은 타당합니다. 그러나 이를 Session 전체 메모리 한도로
해석하면 안 됩니다. 송신 경로는 다음 세 부분으로 나눠야 합니다.

```text
Room → 예약된 post(handler가 packet/Session 소유) → OutboundQueue → in-flight batch
```

현재 프로토콜 경로에서 Queue와 in-flight의 논리적 payload 합은 보수적으로 `256KiB + 65,542 bytes`
이하로 설명할 수 있습니다. 하지만 그 앞의 post 대기량에는 제한이 없어 **전달 경로 전체의 상한은 아닙니다**.
일반 OutboundQueue API 자체는 256KiB짜리 단일 packet도 받을 수 있으므로 protocol 상한을 적용하지 않은
일반적인 Queue+batch 상한과도 구분해야 합니다. shared packet의 중복 참조, vector capacity, handler·coroutine
할당, socket buffer를 포함한 실제 process 메모리는 이 논리적 byte 합과 다릅니다.

### 6. 1 client와 64 clients의 개선 폭이 다른 이유는?

1 client에서는 자신의 응답을 기다린 뒤 다음 요청을 보내므로 묶을 packet이 적습니다. N clients가 모두 송신하고
각 Move가 N명에게 전파되면 fan-out에 따라 송신 작업이 늘고 batch를 구성할 기회도 늘어납니다. 이는 개선 폭과
일치하는 설명입니다. 실제 batch 개수·크기 없이 줄어든 write 횟수를 단정하지 않고 다음 계측에서 확인합니다.
과거의 9.15배와 Nagle 비활성화 재측정의 7.66배는 서로 다른 측정 조건의 결과입니다.

### 7. io_context.run을 여러 thread에서 호출하면 어디가 위험한가?

지금 Session executor는 일반 socket executor입니다. OutboundQueue의 deque·pending_bytes·closed,
Session의 write_in_progress·stopped·joined_room 상태를 read/writer/deliver/종료 경로에서 함께 접근하므로
다중 I/O thread에서 레이스가 발생할 수 있습니다. std::exchange(bool)은 원자 연산이 아닙니다.
같은 socket의 close/cancel과 작업 시작도 같은 실행 문맥으로 직렬화해야 합니다.

반면 SessionRegistry의 map/set에는 이미 mutex가 있고, Room은 전용 Worker 하나가 변경하며 command Queue도
mutex로 보호됩니다. 이 부분까지 모두 무보호라고 설명하지 않습니다. Session별 strand에 모든 관련 실행 경로를
귀속하는 단계가 필요합니다. strand는 전용 thread를 뜻하지 않습니다. 또한 io_context{1}의 1은 thread 생성
개수가 아니라 concurrency hint이므로 여러 run thread로 확장할 때 생성 설정도 함께 검토합니다.
[Asio strands](https://think-async.com/Asio/asio-1.36.0/doc/asio/overview/core/strands.html)

### 8. closed-loop 벤치마크가 과부하를 충분히 보여주는가?

아닙니다. 현재 client는 응답이 느려지면 다음 송신도 늦어져 유입량이 줄어듭니다. 동일 조건의 end-to-end 성능
비교에는 유효하지만, 생산 속도가 소비 속도를 초과하는 상황이나 수신하지 않는 client의 영향을 충분히 검증하지
못합니다. 별도 시나리오에서 고정 송신률·제한된 burst·수신 중단을 사용하고, 부하 발생기 자체의 대기량에도
상한·timeout을 둡니다. 기존 비교용 benchmark의 의미를 바꾸지 않습니다.

## 실행 순서와 완료 기준

| 단계 | 작업 | 완료 기준 |
|---|---|---|
| 1 | 전달 경로 및 batch 계측 | post 대기 / Queue / in-flight 구분, per-Session high-water, 실제 composed write 시작·완료·오류 기록, 정리 후 gauge 0 |
| 2 | 느린 client·연결 종료·생산 과부하 | timeout 있는 실제 연결 테스트, 정상 client 영향과 대기량 추이 관찰, 필요 시 post 이전 admission 제한, 참조·Registry·Room 정리 검증 |
| 3 | Graceful shutdown | accept 중단, 신규 gameplay 거부, Leave/정리 작업 허용, Session 취소·완료 대기, Worker drain/join과 executor 정리 순서 검증 |
| 4 | Session strand와 I/O 1·2·4 thread | read/write/deliver/close를 동일 strand에 귀속, 상태 정합성·취소 회귀 테스트 후 제한된 성능 비교 |
| 5 | 여러 Room과 Worker 분할 | RoomId별 owner 일관성, hot Room 및 여러 작은 Room 비교 |
| 6 | 다음 병목 한 가지 최적화 | 새 profile 근거와 동일 조건 전후 비교 |
| 7 | Sanitizer·fuzz·soak | 도구 지원 플랫폼 명시, protocol fuzz와 장시간 누수·종료 검증; 가능한 검사부터 앞 단계에도 적용 |
| 8 | v0.2 문서·포트폴리오 | 구현·실험·계획 구분, 코드·CSV·PDF 조건 일치, 실제 본인 판단과 AI 작업 구분 |

종료 순서에서 command Queue를 먼저 전부 닫으면 Session이 제출하는 Leave도 거절될 수 있습니다. 현재
RoomWorker::stop은 이미 accepted command를 drain하고 join하지만, 서버 전체 종료 조율은 없습니다.
새 gameplay의 접수 차단과 필수 정리 command의 수락 여부를 분리해서 설계해야 합니다.

## 계측 정의에서 주의할 점

- 64 clients × 2,000개의 **128,000은 측정 Move command 수**입니다. 구성원이 고정되면 이들의 broadcast delivery는
  계산상 8,192,000건입니다. 여기에 warm-up, join, leave 등의 Event는 별도로 발생합니다.
- `broadcast_delivery_attempts`는 실제 recipient->deliver 호출 시도 수입니다. enqueue 성공이나 socket 완료 수가 아닙니다.
- write batch 수는 Asio composed operation 수입니다. OS syscall 수와 구분합니다.
- bytes_requested는 batch에 들어간 논리적 byte 수, bytes_transferred는 완료 callback이 보고한 byte 수입니다.
  실패한 작업의 partial completion도 구분하고, 상대 수신 완료로 이름 붙이지 않습니다.
- 프로세스 시작부터의 누적 통계와 benchmark 측정 구간 통계는 다릅니다. 첫 계측에서는 범위를 명시하고,
  128,000개 측정 Move만의 효과를 주장하려면 이후 phase 경계와 delivery 완료 기준을 추가해야 합니다.
- RoomWorker에는 이미 처리·거절 command 및 Event callback 실패 횟수가 종료 summary에 있습니다.
  이 값의 의미를 유지하며 실행 중 관찰 가능하게 확장합니다.
